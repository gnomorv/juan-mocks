How ADP Works

Overview​

The Autonomous Dev Pipeline (ADP) takes a piece of work from an idea to merged, checked code. Agents do the planning, the building and the checking. A person approves at fixed points and merges.

ADP is made of 11 skills. A skill is a written set of instructions for one stage. You start a skill from a tool such as Claude Code, and the agent follows it step by step. This page explains the whole process in order. Each skill has its own page with the detail.

The Whole Process​

PLAN      1. Prepare the repository        adp-setup          once per repository
          2. Turn the project into issues  adp-plan-project
          3. Plan the epic                 adp-plan-epic
          4. Plan the issue                adp-plan-issue
                                           a person approves the plan

BUILD     5. Build the issue               adp-issue          or adp-epic for a whole epic
          6. Open the pull request         adp-pr
                                           a person merges

CLOSE     7. Check and close               adp-qa

BACKLOG   Runs alongside: sorts the open issues and starts the ones that are ready
                                           adp-groom, adp-dispatch, adp-queue

Everything the pipeline does is written on the issue in Clara Studio: a comment for each step, the approvals and the results. An agent that starts later reads those comments to know where the work stands.

Words to Know​

WordMeaning
ContractThe approved plan of an issue: its goal, the points that must be true at the end, and how each point is checked.
GateA point where the work must pass a check or an approval before it continues.
RunOne execution of a skill on an issue.
ParkA run that stopped and waits for a person. The issue is set to Blocked until the person answers.
ProfileThe file that tells the skills how to test and build a repository.
EpicA large piece of work, split into stories.
StoryOne issue inside an epic.

Step 1: Prepare the Repository​

Skill: adp-setup. It runs once for each repository.

  1. The skill reads the repository to find the commands for tests, coverage and build.
  2. It shows you the proposed profile. You confirm it or change its values.
  3. It saves the profile on its own branch and runs the checks once, to prove the profile works.

Every later skill reads the profile to know which commands to run.

Step 2: Turn the Project into Issues​

Skill: adp-plan-project. It applies when the work comes from a project with an estimate.

  1. The skill finds the estimate of the project and checks that it is final and approved.
  2. It tells you what it is about to file.
  3. It files one epic, or one for each release, and one placeholder story for each line of the estimate.

A placeholder story is a rough story. It is planned in detail later.

Step 3: Plan the Epic​

Skill: adp-plan-epic.

  1. The skill sets the list of stories, their order and which story depends on which.
  2. It writes the epic plan: the objective, what the stories share, the scope and the tests that prove the stories fit together.
  3. Reviewers read the plan.
  4. The skill plans the first story in full. The other stories stay as placeholders.
  5. You approve the epic plan and the first story together.

Later stories are planned one at a time, when their turn comes, against the work already finished.

Step 4: Plan the Issue​

Skill: adp-plan-issue. Every issue passes through this step.

  1. The skill reads the issue and sizes it. If the issue is too big, it proposes a split.
  2. It writes the contract and saves it as the description of the issue.
  3. If the change shows on screen, a mock-up is agreed.
  4. Product, architecture and security reviewers read the contract.
  5. You approve the contract at the plan gate. The issue moves to Ready for Dev.

No code is written before the contract is approved.

Step 5: Build the Issue​

Skill: adp-issue.

  1. Tests first. One test is written for each point of the contract. Each test must fail first.
  2. Code. The smallest change that makes the tests pass. The tests are not edited at this step.
  3. Gate. Every check of the repository runs. A failed gate goes no further.
  4. Second look. The tests are checked for gaps. If the change shows on screen, you see the screenshots and say whether they look right.
  5. Review. Architecture and security reviewers read every change.
  6. Simplify. The change is made smaller without altering what it does.

The work is split between roles, so that no role checks its own work: one writes the tests, another writes the code, others review.

Step 6: Open the Pull Request​

Skill: adp-pr.

  1. The skill brings the branch of the issue up to date with the shared code.
  2. If that changed reviewed files, they are reviewed again.
  3. It opens the pull request and waits for the automatic checks.
  4. It hands the pull request to you. The skill itself never merges.

Step 7: Check and Close​

Skill: adp-qa. It runs after the pull request is merged.

  1. The skill looks for proof of each point of the contract. A comment that only says a point is met does not count.
  2. It posts one result comment on the issue.
  3. It moves the issue once.
OutcomeWhere the issue goes
Every point is metClosed, or Ready for Release
A point is not metReady for Dev, with a bug issue
Proof is missing, or a person must answerBlocked, with the reason

The skill does not check work it built itself.

One Issue or a Whole Epic​

The steps above describe one issue. An epic follows the same steps, with one difference in the Build phase.

One issueA whole epic
Planadp-plan-issueadp-plan-epic, then each story is planned when its turn comes
Buildadp-issueadp-epic builds every story in order, the way adp-issue does
Where the code goesThe branch of the issueEach finished story is added to one shared branch, the epic branch
Pull requestOne for the issueOne for the whole epic. No pull request for each story

After each group of stories, adp-epic runs every check on the combined result, to prove the stories work together.

Keeping the Work Moving​

Three skills manage the list of open issues, so the steps above always have work to take.

OrderSkillWhat it does
1adp-groomSorts every open issue into four groups: ready, needs planning, needs a person, stale. It writes one report of what people owe.
2adp-dispatchReads that report and starts the work: planning for the issues that need a plan, building for the issues that are ready. It never starts the same issue twice.
3adp-queueWorks through the issues assigned to you with nobody present, one at a time. For each one it starts adp-issue, waits and records the result.

Where a Person Decides​

The agents stop at these points and wait for you.

WhenWhat you decide
Setup proposes a profileWhether the profile is right
A contract or an epic plan reaches its gateWhether to approve the plan
The change shows on screenWhether the screenshots look right
A reviewer finds a critical problemHow to continue
A point of the contract must changeWhether the scope changes
The pull request is readyTo merge it
The final check cannot find proofWhether to accept the point or not

When a run stops, it leaves a comment on the issue, sets the issue to Blocked and asks one question. The run continues from the same step once you answer.

References​

  • adp-setup — Prepares a repository for the pipeline
  • adp-plan-project — Files the epic and stories of a project
  • adp-plan-epic — Splits an epic into stories
  • adp-plan-issue — Turns one issue into an approved contract
  • adp-issue — Builds one issue from its contract
  • adp-epic — Runs every story of an epic in order
  • adp-pr — Opens the pull request and waits for the checks
  • adp-qa — Checks a merged issue and closes it
  • adp-groom — Sorts the open backlog
  • adp-dispatch — Plans and launches the issues that are ready
  • adp-queue — Works a to-do queue one issue at a time

CLARA STUDIO · WORKING PROPOSAL

Keeping the help docs up to date with ADP

How to make every help docs update part of the Autonomous Dev Pipeline, in five pieces and two phases.

November 24, 2026 · Based on the skills and workflow documents of Clara Studio. Nothing here has been run or tested yet.

This deck walks through the idea in order: where we are today, how ADP works, the five pieces of the proposal, how to roll it out, and what is still open. It is a working proposal, not a decided standard.

THE GOAL

An issue cannot close until its help docs change is published.

Users see a feature and its guide on the same day, and nobody has to remember to ask for it.

This is the one outcome the whole proposal serves. Help docs means the help site for Clara Studio users, at docs.clarastudio.ai, kept in its own repository. One page of it is a guide.

WHERE WE ARE

Two pipelines, and only one knows about the help docs

In use

The work-issue pipeline

The earlier set of skills. It is not ADP.

  • It has a help docs step for each change.
  • Set up on November 11, 2026. Two changes have used it so far.
  • The agent decides whether a change needs the help docs. Nothing checks that decision.

In use

ADP, the Autonomous Dev Pipeline

The pipeline meant to replace it: 11 skills and 14 reference documents.

  • None of its 11 skills mentions the help docs.
  • No skill writes the help docs change, opens the docs PR or checks it was merged.
  • An issue shipped through ADP can leave the help docs behind.

In both pipelines, nothing re-checks the guides already written.

The work-issue pipeline is /work-issue, /pr, /merge and /production-release. Its help docs steps were added when the help docs moved to their own repository. Two docs PRs have gone through, both merged on November 19. Some ADP runs carried a Help docs line anyway, only because the agent also reads the rules of the Clara Studio repository.

HOW ADP WORKS

ADP takes an issue from plan to close in six steps

1

Project Intake

A client request becomes approved documents. The estimate holds the Ticket plan.

project-intake

2

Plan

The Ticket plan becomes issues. Each issue gets a contract of at most 5 criteria.

adp-plan-project · adp-plan-epic · adp-plan-issue

3

Build

ADP writes the tests and the code, and opens the Clara Studio pull request.

adp-issue · adp-pr

4

Check

The merged issue is checked against its contract, then waits for the release.

adp-qa

5

Production release

A person runs the release. ADP never merges into the main branch.

Outside ADP

6

Close

ADP closes the issue after the release, and not while a criterion is unmet.

adp-qa

Three rules matter for the proposal. One: an issue is built and checked against its contract. Two: ADP never merges into the main branch, a person releases. Three: only adp-qa closes an issue, and never while a criterion is unmet. Small work can enter at step 2 without Project Intake. ADP works in one repository per run.

THE IDEA

No new skill. The help docs travel inside each issue.

State the help docs in the issue, and ADP’s own contract and checks carry them to the end. Five pieces are needed.

ADP already builds against a contract and refuses to close an issue with an unmet criterion. So instead of writing a new help docs skill, the proposal puts the help docs requirement into the issue itself, where those existing mechanisms pick it up.

THE PROPOSAL

Five pieces make the help docs part of ADP

1

The issue names the help docs

It includes the Help docs statement, and its contract gets two help docs criteria.

2

A page to guide map

One small file linking each app page to its guide, so no guide is missed.

3

A linked help docs issue

The help docs change is its own issue, run by ADP in the help docs repository.

4

A reviewer checks it

The help docs change is reviewed together with the code, through a review criterion.

5

The issue waits

A criterion keeps the issue open until the docs PR is merged.

The Help docs statement is one line in the plan of an issue: either the guides to update or add, or none with the reason. Pieces 4 and 5 are the two help docs criteria named in piece 1. Piece 3 exists because ADP works in one repository per run, and the help docs live in a second repository.

WHAT CHANGES IN AN ISSUE

Three added lines carry the whole requirement

EXAMPLE ISSUE · “ADD A BUTTON”

Plan: add the button to the board toolbar.

Help docs: Project Board guide, update the toolbar section.

CONTRACT CRITERIA

1 to 3. The button works as described.

4. A reviewer confirms the help docs change matches the new behaviour.

5. The docs PR is merged.

The Help docs statement

Names the guides to update or add. If none, it says “none” and why.

Two help docs criteria

One is judged by a reviewer during the build. The other is checked after the release.

Example wording, written for this deck. The final text of the criteria is still to be agreed.

The orange lines are what the proposal adds. Everything else is what an ADP issue already has. Note the cost: a contract allows at most five criteria, and the help docs take two of them. That limit is one of the open decisions.

Read each column top to bottom: the first row is the code, the second is what happens to the help docs at the same step. The docs PR stays open on purpose, so the help docs never describe a feature users do not have yet. One caution for step 3 in the second row: ADP has never been run in the help docs repository.

HOW TO ROLL IT OUT

Start by hand, then let ADP enforce it

PHASE 1

By hand

What changes

Nothing in ADP. Whoever writes the issue adds the Help docs statement and the two criteria.

Result

Works issue by issue, starting now. Nothing enforces it.

PHASE 2

Enforced

What changes

One paragraph in the Protocol, one of the 14 ADP reference documents.

Result

ADP refuses to plan an issue that changes what users see and lacks the statement and criteria.

Phase 1 costs nothing and lets us try the idea on a few real issues. Phase 2 is a small written change, but it touches an ADP reference document, so it needs the agreement of whoever owns ADP.

STILL TO DECIDE

Eight questions to settle before phase 2

1. Can ADP run in the help docs repository? Never tested.

2. Can a reviewer read a change in another repository?

3. Which branch does the docs PR target, main or dev?

4. Do two help docs criteria fit the limit of five per contract?

5. Can ADP captures be reused as help docs screenshots?

6. Should Project Intake name the guides?

7. Who re-checks the guides already written, at each release?

8. How do we detect a change nobody documented?

Suggested first step: try phase 1 by hand on two or three real issues, and answer questions 1 and 2 with one test run.

Questions 1 and 2 decide whether pieces 3 and 4 work at all, so they come first. Questions 7 and 8 are not solved by this proposal: it covers new changes, not guides that are already out of date. The suggested first step is my recommendation, not something already agreed.

Project Intake, ADP and the Help Docs

How they connect today, where the gap is, and how the proposal closes it.

In short

  • Project Intake feeds ADP today. Intake ends with a signed ticket plan, and a person starts ADP from it.
  • The help docs are the gap. No Project Intake skill and no ADP skill mentions them, so work shipped through ADP has no help-docs step.
  • The proposal closes that gap inside ADP. The guide is named in each issue's contract, and the issue cannot close until the guide is published.
  • Spec changes are a separate idea. They are discussed, not built, and the proposal does not depend on them.
Exists works today, according to the skills and the workflow documents Gap nothing covers this today Proposed part of the proposal, does not exist yet Idea discussed, not built and not part of the proposal Outside ADP done by a person, because ADP does not do this step

ADP is the Autonomous Dev Pipeline. Project Intake is the chain of skills that takes a client request to a signed scope.

  • An issue can be planned, built and checked with no guide change.
  • Some runs add a Help docs: line anyway, because of a rule in the repo. Nothing enforces it.

2The older path has a help-docs step

The pipeline that ADP is meant to replace does carry the help docs. This is the step that has no counterpart in ADP yet.

MomentSkillWhat it does for the help docs
Plan/work-issueThe plan states Help docs: <guides> or Help docs: none, <why>
Pull request/prOpens the guide pull request first, then the code pull request
Merge to dev/mergeLeaves the guide pull request open
Release/production-releaseMerges each open guide pull request whose issues all shipped

The rule: a change needs a help-docs update when it alters what a person sees or does. Internal refactors, tests and pipeline changes do not.

What changed and why

Project Intake already feeds ADP. Neither of them mentions the help docs, so work shipped through ADP has no guide step. The proposal adds four pieces, all inside ADP, with no new skill.

  1. The issue names the guide. A Help docs: line in the issue, and two guide criteria in the contract. The planner only acts on what the issue says.
  2. A linked guide issue. The guide change is its own issue in the User Guide repo. ADP works in one repository per run.
  3. A reviewer checks the guide. A review criterion asks whether the guide change covers the page. The guide is judged with the code, not after it.
  4. The issue cannot close without the guide. A criterion waits for the guide pull request to be merged. Today a forgotten guide goes unnoticed.
